# Catz-Embroidery — architecture

> **Status:** settled by `docs/decisions/D001.md`. The crates exist when M0's exit
> criteria pass — until then this file describes the target, not the code.

## 1. Crates and the dependency matrix

A decoupled crate ecosystem, one crate per responsibility, every edge declared in
`matrix.toml` and held by `tests/arch.rs`. The model crate is the SSOT; apps are thin
consumers; nothing depends on an app; the renderer lives in the apps, never in the
vocabulary crate.

| Crate | Owns | Depends on |
|---|---|---|
| `emb-data` | DST/PES/CSV readers + writers — typed, bounds-checked, structured errors | — |
| `emb-model` | the single stitch model (paths, stitches, colours, transforms) + algorithms (hatch, satin, trace, TSP, boolean shapes) | emb-data (tests) |
| `emb-draw` | the preview draw-list vocabulary + visual identity — one source, renderers can't drift | emb-model |
| `emb-editor` (app) | interactive editor | emb-data, emb-model, emb-draw |
| `emb-viewer` (app) | design viewer | emb-model, emb-draw |
| `emb-converter` (app) | image → embroidery (UI, like the Java original) | emb-data, emb-model, emb-draw |
| `emb-infinitedraw` (app) | infinite-canvas drawing | emb-model, emb-draw |
| `emb-launcher` (app) | the hub: app choice, language, update check | — |

## 2. Rendering

eframe with the `glow` backend (OpenGL 2.1+) — immediate mode, closest to the
Processing `draw()` paradigm, and it runs on machines whose GPU has no DX12/Vulkan.
Two mandatory performance techniques:

- **Viewport culling** — per-frame work is proportional to what is visible, never to
  the whole design (a 100k-stitch design costs a few hundred segments on screen).
- **Overview texture cache** — the full design rasterised once, invalidated only on
  edit; the design is static between edits, so the per-frame cost stays near zero.

The heavy work (hatch, satin, TSP) is one-shot per edit and runs in the model crate —
no UI involvement, trivially testable, fast.

## 3. Formats

DST, PES, CSV — see `docs/FORMAT.md`. Every writer is tested against its reader on
real fixture files committed in the repo, and the Rust writers byte-compare against
fixtures generated by the Java suite.

## 4. Where the Java shape survives

The Java code already has the right spine: PEmbroiderGraphics is the de-facto SSOT the
four apps consume. The rewrite keeps that spine and makes it structural (dependency
graph), so the divergence that exists between the Java apps cannot recur.

## 5. Rejected shapes

Named in D001 with their costs: wgpu backend (DX12/Vulkan required), GDI (Windows-only,
re-implements everything), iced (second data model), one crate for all apps (every app
forced onto the same dependency set), DST-only first (M4 blocks), porting without fixtures
(0.1 mm errors show on the machine, not in tests).
