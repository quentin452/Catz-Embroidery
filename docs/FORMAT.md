# Catz-Embroidery — formats

What the machine formats do. Facts below were measured on real files generated by
the Java suite (`tools/java-fixtures/GenFixtures.java`) and are held by the fixture
tests in `crates/emb-data/tests/fixtures.rs`.

**Scope rule (D001, amended):** a format enters M1 only with a named consumer in
the Java suite's apps. Consumers measured 2026-08-16: the converter imports PES and
exports PES/SVG/DST; the editor exports PES/DST. EXP/VP3/PEC/JEF/GCODE/PDF/PNG/TSV
exist in the Java writer with no consumer — they do not enter.

## PES (read + write)

Brother format. The only format with a (broken) reader in the Java suite — see
`docs/LESSONS.md`; the Rust reader is written correct.

- File: `#PES0001` (v1) or `#PES0060` (v6) magic, then a 4-byte LE offset to the
  PEC section.
- PEC section (512 bytes): `LA:` title line (20), 12×0x20, 0xFF, 0x00, icon dims
  (48/8, 38), 12×0x20, palette count (n-1), n palette indices (1-based, into the
  standard 64-colour table), 0x20 fill.
- PEC stitch block: `00 00`, u24 LE block length, `31 FF F0`, width u16 LE,
  height u16 LE, `1E0`, `1B0`, two u16 BE offsets, then records:
  - short: 2 bytes, each a 7-bit signed delta (bit 6 = sign);
  - long: 2× u16 BE with bit 15 set, 12-bit signed delta (bit 13 = trim flag);
  - colour change: `FE B0` + a flag byte, mapped through the palette in order;
  - end: `FF`.
- The reader reconstructs absolute positions by accumulating deltas. The design's
  bounds come back as `[0, 0, w, h]` (the format carries rounded extents, no
  origin); `jumps` are not representable in the PEC stream.
- The writer emits only v1; the reader accepts v1 and v6 magics (the PEC section
  parses identically).
- **Writer quirks kept for byte-fidelity** (measured, `docs/LESSONS.md`): the
  first stitch reads back as three identical points; the trim flag appears only on
  the first stitch's long form.

## DST (write)

Tajima format. Write-only in the suite — no consumer for a reader.

- Header (512 bytes): `LA:` title, `ST:` stitch count, `CO:` colour blocks − 1,
  `±X:`/`±Y:` bounds, `AX:`/`AY:` last stitch position, `MX:`/`MY:` zeros, `PD:`,
  0x1A, spaces to 512.
- Records (3 bytes): balanced signed delta encoding with the y axis flipped
  (`encodeRecord` ladder, max ±121 per record); jumps split long moves into
  sub-records; `0xC3` colour change, `0xF3` end.
- **Deviation** (measured, `docs/LESSONS.md`): the Java never writes the END
  record; the Rust writer does.

## SVG (write)

Export/debug format, string-generated. The most diffable format for porting
checks.

- One `<path>` per colour/jump run: `stroke="#rrggbb"`, points `M x,y L x,y…`,
  coordinates formatted with 3 decimals and a dot (the Java is locale-dependent —
  measured, `docs/LESSONS.md`).

## Round-trip rule

Every writer is tested against the Java-generated fixture byte for byte (DST with
the documented END deviation, PES exactly), and PES round-trips through its reader
(positions exact; colours quantised to the palette — compared by palette index).
