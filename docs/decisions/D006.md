# D006 — The PES palette: unique colours, clamped to what the format can express

> Status: settled 2026-08-16.

## Decided

`write_pec_header` builds the PEC palette from the design's **unique colours
in encounter order**, clamped to 256 entries. The reader maps colour-change
records onto the palette **modulo its length**. Both landed after the first
real multicolor fill (the converter on cat.png: 1746 colour runs, 16 cycling
colours) exposed the Java's behaviour: its palette is a *consecutive-run*
dedup with the unique-colour dedup left commented out
(PEmbroiderWriter.java:788), and a design whose colours cycle (every
converter multicolor fill) overflows the fixed PEC header — the Java writes
1746 palette bytes and no padding, corrupting the file.

**Why 256, not 463:** the PEC header reserves 463 palette slots (512 header
bytes minus the fixed fields, the Java's `463 - palette.size()` padding
target), but the palette-**count byte** is a single u8 (count + 1 entries).
Only 256 entries are expressible in a conformant file. The port clamps to
256; the pad still targets 463 slots.

**The reader wrap:** the Java writer's colour-change records only alternate
threads 1/2 (its `color_two` toggle) regardless of the design's colours — the
record carries no position signal, so the reader's change counter is the only
index. A design with more changes than palette entries (the converter's
multicolor fills) now wraps around the palette instead of refusing. The
resulting colours still come from the palette, in order, cycled.

## Refused

- **Mirroring the Java's corruption** — the no-op padding and truncated
  count byte for palettes past the header overflow the fixed layout and
  misalign the icon and block sections; the machine cannot read it, and the
  converter's multicolor save would never work.
- **The consecutive-run dedup** — it counts runs, not colours: 1746 entries
  for a 16-colour fill. The Java's own (commented-out) intent was a unique
  palette; the fixture byte-compares are unaffected (their colours never
  cycle, so both dedups agree).
- **A hard error on `colour changes >= palette len`** — the reader's pin-4
  refusal, dropped here by the wrap: the file is not malformed (threads 1/2
  are valid), the reader's counter interpretation is the heuristic that ran
  out.

## What catches a violation

- A PES with a palette count byte above 255 — the clamp is the only writer
  path; the reader caps `palette_len` at 256.
- A panic in `write_pec_header` on any design — `PEC_PALETTE_MAX` and the
  `saturating_sub` pad make the >256 path unreachable; the regression test
  `pes_clamps_a_palette_larger_than_the_header` (500 distinct runs) guards
  it.
- A claim that the palette matches the Java's bytes on a cycling-colour
  design — it deviates by this ruling (the Java is corrupt there); the M1
  byte-compare fixtures (non-cycling) are unchanged.
