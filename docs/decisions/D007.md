# D007 — The PES writer measures deltas from the offset origin

> Status: settled 2026-08-16.

## Decided

`pec_encode` accumulates deltas from the **offset origin** the header's
offset words declare (`-bounds[0]`, `-bounds[1]`), not from 0. The Java's
writer starts `xx = yy = 0` (PEmbroiderWriter.java:895) while its offset
words write `0x9000 | -bounds[0]` — the two disagree whenever
`bounds[0] != 0`, and the file then reads back shifted by `-bounds[0]` (a
latent writer/reader mismatch the M1 fixtures never exposed: they all have
`bounds[0] = 0`).

The reader is the validated ground truth (test.pes, checked against
pyembroidery: the deltas accumulate from the offset origin). The writer
must agree with it.

**Found by** the infinite canvas mode's content-centred save (the first
writer output with a nonzero bounds origin since M1): the read-back was
shifted by `-bounds[0]`. The editor's centred save (bounds `[-512, ...]`)
was silently misaligned the same way — its round-trip test only checked a
range, so it stayed green.

## Refused

- **Keeping the deltas-from-0** (the Java's bytes): files with a nonzero
  bounds origin misplace when read by anything honouring the offset words
  (the reader, pyembroidery, machines). The Java is inconsistent with its
  own format here; the M1 byte-compare fixtures all have `bounds[0] = 0`,
  where the two conventions agree and the bytes are unchanged.
- **Changing the reader instead**: the reader's origin semantics are the
  validated, third-party-proven reading; the writer is the one that
  disagrees with the format.

## What catches a violation

- A regression test is the gate: `pes_roundtrips_designs_with_a_nonzero_origin`
  asserts an exact read-back of a design with `bounds[0] = -512` (the
  editor's centred canvas); the infinite canvas's content-centred save test
  asserts exact points too.
- A claim that a nonzero-origin design byte-matches the Java's output — it
  deviates by this ruling; the M1 fixtures (origin 0) are unchanged.
