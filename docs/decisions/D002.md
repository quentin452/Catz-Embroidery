# D002 — Float comparison tolerance for geometry algorithms

> Status: settled 2026-08-16.

## Decided

Algorithm outputs (polylines in mm) are compared against Java-generated fixtures
with a tolerance of **0.001 mm** per coordinate. The tolerance is written into
every geometry test explicitly — it is part of the assertion, never a global
constant swallowed in a helper.

**Why 0.001 mm:** the machines stitch on a 0.1 mm grid (DST and PES units are
0.1 mm; the writers already round to 0.1 mm when encoding). Two designs differing
by 0.001 mm produce the same file, byte for byte. The tolerance is 100× finer than
the machine resolution, so it cannot mask a real deviation — it only absorbs
last-ulp noise between the Java `(float)Math.sin` and the Rust `f32` libm, which
are not guaranteed identical.

**Byte-compare stays** for the binary writers (DST/PES) and the string writer
(SVG) — M1's fixtures remain exact.

## Refused

- **Exact float comparison** (`assert_eq` on f32): a 1-ulp libm difference would
  fail the gate on a non-bug. The fixture test would become a flaky oracle.
- **A looser tolerance (0.1 mm):** that is the machine grid itself; a 0.05 mm
  regression would pass. 0.001 mm separates "noise" from "error" with 100× margin
  on both sides.

## What catches a violation

- A geometry test whose assertion has no explicit tolerance — code review (a
  helper `assert_polylines_close` that hardcodes 0.001 is fine: the constant is
  visible in the helper's signature in the test file).
- A writer fixture test using tolerance instead of byte-compare — the M1 tests.
