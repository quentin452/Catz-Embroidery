# D010 — The editor's CONCENTRIC hatch: the isolines raster path, not hatchInset

> Status: settled 2026-08-17.

## Decided

The Java editor's CONCENTRIC hatch mode (the M4 named exception, ROADMAP) is
ported into the Rust editor (`apps/emb-editor/src/stitch.rs` + `doc.rs`, the
Parallel/Concentric toggle in the layer row, Main.java:495-503).

**CONCENTRIC is the isolines raster path, not hatchInset.** The D003 deferral
named `hatchInset` as "the editor's CONCENTRIC" — the VECTOR path a
`beginShape`/`endShape` call would take. The editor never calls it: `stitchLayer`
rasterises the layer and calls `E.image(lay.render, 0, 0)` (Main.java:263), and
`image()`'s CONCENTRIC routes through `hatchRaster` → `isolines` (the
distance-transform rings). The subagent audit (2026-08-17) measured this
directly. `isolines` and the contour tracer are ALREADY ported and
fixture-compared in M2 (`emb_model::hatch::isolines`, `trace::find_isolines`),
so the editor's CONCENTRIC is wiring, not an algorithm.

**Element-local, like the cull.** Each PLY element's fill mask
(`Raster::fill_polygon`, the D004-class oracle at 1 px per mm) is fed to
`isolines` at the layer's hatch spacing; the rings are the distance-transform
levels INSIDE the shape (the polarity the `isolines.txt` fixture pins — the
first ring of the 15-radius fixture circle sits at radius ~11). A culled layer
subtracts the later masks first (the D009 path), so the holes the cull cuts are
part of the mask the isolines read; an unchanged mask takes the exact unculled
isolines output.

**The boundary outline stays out.** The Java's `image()` pushes each found
contour directly as a polyline when `!isStroke && HATCH_MODE == CONCENTRIC`
(PEmbroiderGraphics.java:4876-4880). The Rust editor's PLY path is fill-only
and its layer model has no per-layer stroke toggle yet — the boundary contour
enters with that toggle (the TANGENT/PERPENDICULAR stroke-mode follow-up, still
deferred per D003/D004). Named, not silent.

## Refused

- **Porting `hatchInset` (the vector offset path)** — the editor never calls
  it; the raster isolines path is what CONCENTRIC actually does, and it is
  already ported. Porting the vector path would add an algorithm no consumer
  reaches.
- **The boundary-contour push** — needs the stroke-mode toggle (its Java
  trigger is `!isStroke`); it enters with that follow-up.
- **Layer-wide raster (Java-faithful whole-layer mask)** — re-opens the
  accepted per-element stitch structure, the D009 refusal for the same reason.

## What catches a violation

- A claim that CONCENTRIC runs `hatchInset` — it runs `isolines`, by this
  ruling (measured: the editor's `E.image()` call site).
- A fixture test against the Java's editor CONCENTRIC output — none exists,
  by this ruling (the isolines port's M2 fixtures are the algorithm level; the
  editor composition is invariant-tested like the cull, D009).
- A CONCENTRIC ring outside its element's shape — the isolines polarity keeps
  rings inside the fill mask; a test pins the span.
