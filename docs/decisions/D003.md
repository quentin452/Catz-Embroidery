# D003 — Deferred: the stroke path (PERPENDICULAR/TANGENT)

> Status: settled 2026-08-16.

## Decided

`strokePolyNormal` / `strokePolyTangentRaster` (the `_stroke` path the converter
uses with `strokeMode(PERPENDICULAR)`) are **deferred**. M2 keeps the hatch modes
(PARALLEL, CROSS, CONCENTRIC, SPIRAL, PERLIN); the stroke enters when the
converter app is built (M5).

**Why deferred, measured:** the Java implementation is not an algorithm — it
delegates rendering to Java2D: stroked polylines (SQUARE caps, MITER joins,
weight = stroke weight), a DILATE filter, then perpendicular sampling of the
pixels. Reproducing the output within the D002 tolerance requires replicating
sun.java2d's rasterizer pixel-for-pixel (a multi-day effort with real risk), and
one pixel of raster difference shows up as ~1 mm of output shift — the 0.001 mm
tolerance cannot absorb it. Deferring lets the converter (M5) decide the
comparison level instead (e.g. raster-level comparison, or a re-evaluation of the
stroke design).

## Amendment — 2026-08-16 (the class, not just the stroke)

Measuring PERLIN (`perlinField` → `customField`) showed the same Java2D
dependency: the field walks are bounded by sampling a raster in which the walked
lines are DRAWN with `pg.strokeWeight(d)`. The stroke was not the exception —
**eleven algorithm families render through `app.createGraphics`** (measured, the
callers at PEmbroiderGraphics.java:1512, 1567, 1612, 1762, 1884, 2121, 2577,
2661, 2800, 2920, 4972):

`offsetPolygon`, `insetPolygonsRaster`, `outsetPolygonsRaster`,
`strokePolyTangentRaster`, `strokePolyNormal`, `strokePolyNormalAng`,
`hatchSpiral_v2/v3/v4`, `hatchPerlin`, `customField` (PERLIN).

This ruling extends to the whole class: each of these algorithms is deferred
until the Java2D-rasterization question is decided (M5, with the converter in
front of it). The vector-pure remainder — `hatchParallelComplex`, `hatchInset`
(the editor's CONCENTRIC) — stays in M2's scope.

## Refused (for now)

- **Porting the Java2D rasterizer subset** (thick strokes + caps + joins +
  DILATE): multi-day, pixel-exactness uncertain, and nothing consumes the stroke
  until M5 anyway (pin 3 works both ways: no consumer TODAY for a perfect port).
- **Rewriting the stroke as offset curves**: a cleaner algorithm, but the output
  would differ from the Java model's by design — a deviation that deserves its
  own ruling with the converter in front of it, not one taken in the dark.

## What catches a violation

- A claim that a deferred algorithm is ported — the ROADMAP row for M2 names
  what remains.
- A fixture test for a deferred algorithm — it does not exist yet, by this
  ruling.

## History

- 2026-08-16 (amendment): the same measurement on customField extended the
